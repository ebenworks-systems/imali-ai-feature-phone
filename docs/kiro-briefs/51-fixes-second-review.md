You are working in this repository, the Imali AI feature-phone ledger. Read the steering files in .kiro/steering/ and the specs in .kiro/specs/server-and-store/, .kiro/specs/dialled-menu/, .kiro/specs/text-messages/ and .kiro/specs/browser-phone/ first. A second reviewer read the code before the live demo goes public and found six faults; each is confirmed. Fix all six, and the small seventh item below, each with a test that fails before the fix and passes after, and note each in the matching spec (a requirement where the spec was silent, and a new ticked task).

1. The browser routes create shops. POST /api/phone/ussd with text "A*1" and POST /api/phone/sms with "hi" then a name both sign up a new shop for any demo number that has none, without the per-address demo limit or the 5,000 cap (src/server/routes/browser.ts). One client can walk through all 10,000 demo numbers, after which "Start demo shop" fails for every judge. Fix: on /api/phone/ussd and /api/phone/sms, a demo number with no shop is refused before any handler runs (404 with a short plain sentence such as "No demo shop on this number. Press Start demo shop.") and nothing is written. Only POST /api/phone/demo makes demo shops. Make the page treat that 404 the way it already treats a stale number on the ledger call: return quietly to the first-visit state. Update docs/judges.md and docs/run-the-demo.md where they describe this.

2. Demo shops never expire, so the cap fills for good over the judging weeks. Add store methods that delete demo shops (phone starting with the demo prefix only, never any other shop) created more than 7 days ago, together with their records and pending questions, in one transaction on Postgres and the same in memory. Call it on POST /api/phone/demo before the cap check, at most a bounded number of shops per call (for example 200), so the cap frees itself. This is housekeeping of invented demo data, not editing a record: say so in money-and-records terms in the server-and-store spec, and make sure no code path can delete a non-demo shop or a single record. Test both stores, including that a shop on a non-demo number of any age is never deleted.

3. The per-address limits are weak. (a) clientAddress in src/server/phone.ts trusts the leftmost X-Forwarded-For entry, which a caller can write. On Vercel, read x-real-ip first (Vercel sets it to the connecting address), then the rightmost X-Forwarded-For entry, then 'unknown'. (b) Every browser route (/api/phone/ussd, /api/phone/sms, /api/phone/demo, /api/ledger, /api/export) also counts against the client address, for example 120 requests a minute per address, as well as the existing per-phone limit. (c) The demo-create limit of 10 an hour per address, and a site-wide ceiling of demo shops made per day (for example 1,000), are kept in the store so they hold across serverless instances: a small table in sql/ (new migration file, never edit an applied one) keyed by a SHA-256 hash of the address with a server-side salt, never the raw address, with old rows pruned. The salt comes from a new variable ADDRESS_SALT (add it to .env.example and the variables table in docs/run-the-demo.md); when it is unset the server uses a fixed built-in salt, so every instance counts alike, and the start line says salt=default. The memory store keeps the same counts in memory. (d) Put a per-instance ceiling on optional model-reader calls (for example 200 an hour across all callers): beyond it the reader is skipped and the rules answer alone.

4. The Africa's Talking callbacks are open when AT_CALLBACK_KEY is unset (src/server/app.ts, src/server/config.ts). Then anyone can read and write the ledger of any non-demo number through /ussd and /sms, and make the server send a text from our Africa's Talking account. Fix: when the Africa's Talking sender is configured (AT_USERNAME and AT_API_KEY set) and AT_CALLBACK_KEY is not, /ussd and /sms answer 503 with a plain sentence and the start line says callback=missing-key; the server still starts and the browser routes still work. With no sender configured (local runs) they stay open as now. Also limit /ussd and /sms per client address and per phone number, and cap the number of non-demo shops (for example 2,000, counted in the store) so the sandbox cannot fill the database. Keep comparing the key in constant time.
